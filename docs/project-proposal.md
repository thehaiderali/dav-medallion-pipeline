## Executive Summary

We will build an automated **Medallion Architecture** pipeline on **Apache Spark (Databricks Community Edition)** that ingests **U.S. large-cap equity market data** from **Yahoo Finance** (via the open-source `yfinance` library), refines it through **Bronze → Silver → Gold**, and delivers a **Power BI** dashboard for price trends, sector performance, and top gainers/losers.

---

## 1. Domain & Source Identification

### Project concept (domain)

**Financial markets — U.S. equity price analytics.**

The project supports portfolio-style questions over a fixed universe of ten liquid large-cap tickers spanning six sectors: how prices move over time, how sectors compare on a given day, and which names lead or lag. This domain is well suited to Spark (time-series joins, window functions, aggregations) and to the Medallion pattern (immutable raw quotes vs. cleansed facts vs. BI-ready KPIs).

### Data source (exact reference)

| Item | Detail |
| --- | --- |
| **Primary source** | [Yahoo Finance](https://finance.yahoo.com/) public quote endpoints (historical OHLCV and company reference fields) |
| **Access method** | Python [`yfinance`](https://pypi.org/project/yfinance/) (v0.2.51), no API key or paid subscription |
| **Documentation** | [yfinance project docs](https://github.com/ranaroussi/yfinance) |
| **Secondary reference** | Per-ticker company metadata via `yf.Ticker(ticker).info` (sector, industry, headcount, etc.) |

We do **not** scrape HTML pages; ingestion uses the same HTTP-backed interfaces that `yfinance` wraps.

### Ingestion patterns

| Pattern | Purpose | Implementation (planned) | Frequency |
| --- | --- | --- | --- |
| **Full load** | Historical baseline for backtesting and dashboard history | `yf.download(ticker, period="5y")` for each of 10 tickers; append to Bronze partitioned by `_ingest_date` | Once at project initialization |
| **Incremental load** | New trading days only | Read `max(_ingest_date)` from Bronze; `yf.download(..., start=last_date+1)`; append new bars | Daily after U.S. market close (scheduled job) |

**Deletes / corrections:** Yahoo may restate the latest bar; we treat Bronze as append-only audit history and use Silver **`MERGE` on `(trade_date, ticker)`** so the latest ingested version wins for analytics.

**Tickers in scope:** AAPL, MSFT, NVDA, GOOGL, DIS, AMZN, TSLA, JPM, PG, XOM (see root `README.md`).

## 3. Security & Compliance

### PII and sensitive data review

We reviewed raw samples in `sample_data/full_load_sample.csv`, `incremental_load_sample.csv`, and `company_profile_sample.json`.

| Data element | Present? | Classification |
| --- | --- | --- |
| Customer names, emails, government IDs | **No** | N/A |
| End-user IP addresses or device IDs | **No** | N/A |
| Payment card or bank account data | **No** | N/A |
| Individual investor accounts | **No** | N/A |
| **Market prices (OHLCV)** | Yes | **Public market data**, not PII |
| **Company name, sector, website, employee count** | Yes | **Public corporate disclosures**, not personal data |

**Conclusion:** The pipeline processes **no PII**. There are no natural persons identified in the price files; company metadata is aggregate corporate information published for investors.

### Handling strategy

| Layer | Strategy |
| --- | --- |
| **Bronze** | Store as received for auditability; no personal fields ingested |
| **Silver** | Promote only analytical columns (prices, volume, ticker, dates); drop raw dividend/split columns from the fact if not needed for Phase 2 metrics |
| **Gold / BI** | Expose only aggregated market metrics; no row-level personal data |
| **Secrets** | No API keys; Databricks tokens stored in workspace secrets only (not in Git) |

If future scope added user-specific watchlists, we would hash or omit user identifiers before Silver — **out of scope for this project**.

## 4. High-Level Medallion Data Modeling

### Bronze layer (raw)

- **Tables / paths:** `bronze_stock_prices_raw`, `bronze_company_profile_raw`
- **Format:** Delta (or CSV landing) on DBFS / Unity Catalog volume `dav.bronze`
- **Write pattern:** **Append-only**, partition `_ingest_date`
- **Content:** Exact OHLCV from Yahoo plus `ingested_at`, `source`, optional `Dividends` / `Stock Splits` for traceability

### Bronze → Silver processing

| Step | Operation |
| --- | --- |
| Schema conformance | Cast dates to `DATE`, prices to `DOUBLE`, volume to `BIGINT` |
| Naming | `snake_case`; ticker uppercased and trimmed |
| Deduplication | `dropDuplicates(["trade_date", "ticker"])` or Delta **`MERGE`** |
| Quality filters | Drop rows with null OHLC or volume; quarantine invalid OHLC relationships |
| Enrichment | Add `currency = 'USD'`, `source = 'yfinance'`, `silver_loaded_at` |
| Dimension | Build **`company_dim`** (SCD Type 2) from profile JSON — track sector/industry changes |

**Silver model (overview):**

- **`stock_prices_silver`** — fact grain: one row per `(trade_date, ticker)`; partitioned by `trade_date`
- **`company_dim`** — slowly changing dimension keyed by `ticker` with `valid_from`, `valid_to`, `is_current`

### Gold layer (BI-ready)

| Table | Purpose | Key logic |
| --- | --- | --- |
| **`fact_daily_returns`** | Primary fact for charts | `LAG` for prior close, daily/cumulative returns, 20/50-day MAs, 20-day volatility, 52-week high flag; join current `company_dim` |
| **`agg_sector_performance`** | Sector dashboard page | Group by `(trade_date, sector)` — avg return, advancing/declining counts, best/worst ticker |
| **`dim_company_summary`** | Leaderboards & scatter | Total/annualized return, volatility, max drawdown, ranks over full window |

Gold tables are **overwrite or merge by date partition** so reruns are idempotent.

## 5. Business Intelligence & Dashboards

**Tool:** Microsoft **Power BI** (import mode from exported Gold CSV/Parquet, or DirectQuery to Databricks SQL).

### Business questions

1. How have our ten tracked stocks performed over the last five years, and where are they relative to moving averages?
2. Which **sectors** outperformed on a given day or month?
3. Who were the **top gainers and losers** for a selected period?
4. Which companies offer the best **risk–return** trade-off (return vs. volatility)?

### Planned visuals (2–3 specific examples)

| # | Visual | Data | Insight |
| --- | --- | --- | --- |
| 1 | **Multi-line chart** — adjusted close over time, optional 20/50 MA | `fact_daily_returns` | Compare price trends across tickers with slicer |
| 2 | **Matrix heatmap** — sector × month, color = avg daily return % | `agg_sector_performance` | Spot sector rotation and relative strength |
| 3 | **Clustered bar chart** — top 5 / bottom 5 by `daily_return_pct` for selected date | `fact_daily_returns` | Daily winners and losers |

Detailed page layout: `dashboard/dashboard_spec.md`.

**Action for submission:** Push to GitHub and paste the public repository URL on the cover sheet.

### Infrastructure

| Component | Choice |
| --- | --- |
| Compute | **Databricks Community Edition** — single-node Spark 3.5 cluster |
| Orchestration | Databricks Jobs (daily incremental + downstream rebuild) |
| Catalog | Unity Catalog: `dav.bronze`, `dav.silver`, `dav.gold` |
| BI | Power BI Desktop / Microsoft 365 (team access) |

### FinOps and free-tier discipline

| Risk | Mitigation |
| --- | --- |
| Cluster idle cost | Auto-terminate after **20 minutes**; run jobs on schedule, not ad hoc |
| Storage growth | ~3 MB Bronze full load + tiny dailies; Delta compression on Silver/Gold |
| Repeated full loads | **One-time** 5y backfill; daily job fetches **≤10 rows** |
| Yahoo rate limits | `time.sleep(2)` between tickers; retry with backoff; avoid parallel hammering |
| Development | Use **`sample_data/`** and small date filters in notebooks before full cluster runs |
| Testing | `silver/03_data_quality_checks.py` gates Gold promotion to avoid wasted Gold rebuilds |

We estimate total managed data **under 50 MB** for the semester, well below Community Edition storage guidance, with compute dominated by short daily job runs rather than long interactive sessions.
